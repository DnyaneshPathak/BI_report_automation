## 5. ARCHITECTURE — "OLLAMA AS THE BRAIN" WITH A DETERMINISTIC BODY

**Principle: the LLM decides *what to compute*; Python decides *whether it is valid* and *computes every number*.** The LLM never sees raw rows and never produces numbers shown to the user.

```
Upload ─► Loader (no mutation) ─► Profiler (semantic roles) ─► Schema Card
                                                              │
User prompt ─► NLP pre-parser (hints) ──────────────┐         │
                                                    ▼         ▼
                                  Ollama PLANNER (JSON-schema constrained)
                                                    ▼
                                  Plan Validator (deterministic rules)  ◄── repair loop (≤ 2) with Ollama CRITIC
                                                    ▼
                                  Executor (pandas, provenance logged)
                                                    ▼
                                  Renderer (ECharts JSON / tables)  ─►  Power BI exporter
                                                    ▼
                         (only if asked) Ollama NARRATOR → grounded-numbers checker
```

### 5.1 Components (all under `src/bi_automation/`)
`nlp/` (pre-parser, lexicon, column matcher) · `llm/` (ollama_client, prompts, schemas, planner, critic, narrator, grounding, fallback) · `semantics/` (roles, aggregation policy, compatibility matrix) · `planning/` (plan schema, validator, normaliser) · `engine/` (executor, time_grain, filters, provenance) · `charts/` (registry + builders) · `tables/` · `web/` · `powerbi/` · `security/` · `services/`.

### 5.2 Schema Card (what Ollama is allowed to see)
For each column: name, **role** (§6), dtype, unique count, null %, numeric min/max/median (rounded), date min/max and inferred grain, top-5 category *labels only if the column is a low-cardinality dimension* (configurable: `LLM_SEND_SAMPLE_LABELS=false` by default). Also row count and the list of supported chart types and aggregations. **No row values, no free-text cell content, no IDs.** Column names are treated as untrusted text (strip control chars, cap length 80, wrap in delimiters, instruct the model that they are data, never instructions).

### 5.3 Plan JSON (the only thing the planner may output) — validate with a strict JSON Schema + pydantic
```json
{
  "version": 1,
  "needs_clarification": null,
  "requirements": [
    {"id":"R1","text":"monthly sales trend by region as a line chart"}
  ],
  "filters": [{"column":"Order Date","op":"between","value":["2023-01-01","2023-12-31"],"from":"R4"}],
  "items": [
    {"id":"V1","requirement":"R1","type":"visual","chart":"line",
     "x":{"column":"Order Date","grain":"month"},
     "y":[{"column":"Sales","agg":"sum"}],
     "series":{"column":"Region"},
     "sort":null,"top_n":null,"title":"Monthly Sales by Region",
     "dynamic":{"time_grain":["day","week","month","quarter","year"],"default_grain":"month"},
     "confidence":0.93},
    {"id":"K1","requirement":"R2","type":"kpi","metric":{"column":"Ticket No","agg":"count_rows"},"title":"Total Tickets","confidence":0.9},
    {"id":"T1","requirement":"R3","type":"table","group_by":["Country"],
     "metrics":[{"column":"Revenue","agg":"sum"}],"sort":{"by":"Revenue","dir":"desc"},"top_n":10,"totals":true}
  ],
  "assumptions":["'revenue' matched to column 'Sales Amount' (0.82)"]
}
```
Rules: every `column` must exist; `agg` ∈ {sum, avg, median, min, max, count_rows, count_non_null, distinct_count, pct_of_total, rate}; `chart` ∈ registry names (§7); `type` ∈ {visual, kpi, table, matrix, slicer, text(narrative)}; unknown keys rejected; max 40 items.

### 5.4 Thinking ability — a bounded multi-step reasoning loop
Implement as **separate small calls** (cheaper and more reliable than one giant prompt), each with its own JSON schema, temperature 0, fixed seed:
1. **Understand:** split the prompt into atomic requirements R1…Rn (intent, entities, metric words, time words, chart words, filters, top-N, "only/exclude").
2. **Ground:** map each entity to schema columns with scores (use the NLP pre-parser's fuzzy/embedding candidates as hints). If best score < threshold or two candidates within 0.05 → mark ambiguous → clarification question.
3. **Design:** choose chart/aggregation/grain per requirement using the role policy (§6) and chart-selection guidance in the system prompt.
4. **Validate (code):** run the deterministic validator (§6.3, §5.6). Failures are returned to the model as **machine-readable error codes** ("E_AGG_NOT_ALLOWED: Ticket No role=identifier; allowed: count_rows, distinct_count").
5. **Repair (≤ 2 rounds):** the CRITIC call receives the failing items + error codes and returns a corrected plan. If still invalid → drop the item, show it under "Couldn't build" with the reason, never fabricate.
6. **Execute → Verify:** after computing, run sanity checks (non-empty result, no all-null, row-count ≥ 1, totals reconcile with source, no division by zero). Failures create a visible warning on that card.
7. **Narrate (only if requested):** NARRATOR gets **computed facts as JSON** and writes short sentences; the **grounding checker** rejects any sentence containing a number/entity not present in the facts (regex-extract numbers, compare with tolerance after formatting) and regenerates once, else falls back to a template sentence.

Include 8–12 **few-shot examples** in the planner system prompt (stored in `llm/prompts/*.md`, version-controlled), covering: KPI on an ID column (count), "trend" with dynamic grain, "top 10 by", "compare A vs B" (grouped bar, not scatter), "share of" (donut/pie), "distribution of" (histogram), "table of … by …", "waterfall", follow-up edits, vague prompt → clarification, impossible request (zip code vs date) → explanation.

### 5.5 Follow-ups / memory
Keep a per-session **conversation state** = current Plan + list of prior requirements. A follow-up prompt produces a **plan patch** (add / modify / remove item by id or by description: "the second chart", "the trend") applied to the current plan, then re-validated. Never regenerate the whole dashboard for a small edit. Provide an **undo** button (keep last 10 plans in memory only).

### 5.6 Deterministic fallbacks (Ollama unavailable / invalid output)
- Health check at startup and on the prompt page: `GET http://127.0.0.1:11434/api/tags`. If down, show a clear banner with how to start it, and switch to **rule mode**: the NLP pre-parser (+ simplified plan builder) handles clear requests (chart words + column names + aggregation words) and refuses vague ones with a clarification. Rule mode must also obey §4.3 (no auto-generation).
- If the LLM returns invalid JSON twice → fall back to rule mode for that request and tell the user.
- Timeouts: planner 60 s, narrator 60 s, configurable; show streaming progress ("Understanding… Matching columns… Validating… Computing…").

## 6. COLUMN INTELLIGENCE (fixes C2, C5, C8)

### 6.1 Semantic roles (replace the current `analytical_type` usage for decisions)
`identifier` (Ticket No, Invoice No, Order ID, Customer ID, SKU, Transaction Ref), `code_geo` (Zip/Postal/PIN, area code), `phone_like`, `measure_additive` (sales, revenue, amount, quantity, cost, profit, count-like quantities), `measure_nonadditive` (price, rate, ratio, %, age, score, rating, temperature, latitude/longitude, year-as-number), `dimension` (low/medium-cardinality categorical, incl. binary/flags), `dimension_high_card` (names, descriptions), `date`/`datetime`, `text_free`, `constant`.
Decide with **name signals + value signals + LLM-assisted hint (optional)**:
- Name signals (tokenised, case/underscore-insensitive): `id|no|num|number|code|ref|key|uuid|serial|ticket|invoice|order(no)?|sku|zip|postal|pin|phone|mobile` → identifier/code unless values clearly look like a measure (decimals, wide continuous spread, negative values) **and** the name has an additive-measure token.
- Value signals: integer-only, no decimals, high uniqueness **or** repeated references (a ticket number can repeat across rows) , monotonic/sequential, fixed-length digit strings, leading zeros.
- **A numeric-looking column named "Ticket No" must be `identifier`** even if values repeat (the current `unique_ratio > 0.95` gate is wrong). Show the role chip so the user sees it; let the user override by saying so in the prompt ("treat Ticket No as a number").
- Remove "tickets?", "orders?", "transactions?", "bookings?", "visits?", "views?" from the **additive-measure name regex** — those words describe *counts of rows*, not summable columns.

### 6.2 Aggregation policy (hard rules enforced by the validator)
| Role | Allowed aggregations | Default for "total / how many / KPI" |
|---|---|---|
| identifier | `count_rows`, `distinct_count`, `count_non_null` | **`count_rows`** (use `distinct_count` only if the user says unique/distinct/different) |
| code_geo, phone_like | `count_rows`, `distinct_count` | `distinct_count` |
| measure_additive | sum, avg, median, min, max, count_non_null | sum |
| measure_nonadditive | avg, median, min, max | avg |
| dimension | count_rows, distinct_count, pct_of_total | count_rows |
| date | min, max, count_rows, distinct_count | — |
`SUM`/`AVG` on identifier/code/phone columns is **always an error (E_AGG_NOT_ALLOWED)**. "Total X" where X is an identifier means count of rows (client's rule). Power BI/DAX output must follow the same rule (`COUNTROWS`, `DISTINCTCOUNT`).

### 6.3 Compatibility matrix (fixes C5 "zip code vs date")
The validator rejects (or asks for confirmation on) combinations that are statistically/semantically meaningless:
- `identifier`/`code_geo`/`phone_like` as **numeric axis**, in scatter, correlation, regression, trend-over-time-as-measure → rejected.
- `measure_nonadditive` stacked/summed → rejected; latitude/longitude only for geo visuals.
- `date` as a measure; `text_free` as axis; `constant` anywhere.
- scatter needs two numeric measures; box plot needs numeric + optional dimension; line/area need an ordered axis (date or ordinal) — if user asks "compare A and B" with categories, prefer grouped bar.
- Pairing a high-cardinality dimension (> 50 values) on an axis → require top-N or ask.
Each rejection returns a human sentence for the UI, e.g. *"Zip Code is a code, not a quantity, so plotting it against dates has no meaning. Did you want the number of customers per zip code, or a trend of Sales by date?"*

## 9. CHART LAYOUT ENGINE — NO OVERLAPPING TEXT (fixes C3)

Create `charts/layout.py` and use it for every builder. **No hard-coded `nameGap`, rotation or `bottom: 25%`.**
- Measure text: estimate pixel width per label (char count × font-size × 0.6, or canvas `measureText` in `charts.js` after font load) and compute grid margins from the **longest tick label** (left margin for y labels; bottom for rotated x labels), then place **axis titles outside the tick labels** (x-axis name at the axis end/bottom row of its own, y-axis name rotated 90° in its own left gutter). Use `grid.containLabel: true` plus computed extra gutter for axis names.
- Strategy for long/many category labels: wrap to 2 lines (`width` + `overflow:'break'`) → else rotate 30–45° → else switch to **horizontal bar** → else show every N-th label + tooltip with full text. Never print overlapping labels (`hideOverlap` is a last resort, not the plan).
- Legend: top, scrollable (`type:'scroll'`), never over the plot; leave reserved height in the grid.
- `dataZoom` slider only when points > ~60, with reserved bottom space *added to* the label margin.
- Value labels: default **on** for bars/slices/line-ends/peaks when ≤ 20 points; hidden for dense series (tooltip instead); use `labelLayout: {hideOverlap:true}`; number formatting (thousands separators, K/M/B, %, currency symbol from the column).
